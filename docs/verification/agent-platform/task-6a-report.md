## Storage, DTO and concurrency invariants

- Browser keys remain `gr8r.v2` and `gr8r.workspaces.v1`, storage version1. The original `gr8r.v2` bytes remain untouched. When importing gr8r.v2, the first old workspace retains its full graph and the other seed-list workspaces start independently blank, as before. Existing gr8r.workspaces.v1 records each retain their own existing graphs. New workspaces use the existing blank helper.
- DTOs map text IDs, project/task keys, timestamps, descriptions, subtasks, dependency edges and comments without replacing the original records with normalized DTOs. `legacyMetadata` is a clone of each original row. Unknown graph/row fields and literal text survive commands and reload. Bookkeeping never adds keys to `record.data`; even a preexisting graph key named `_panel` is not overwritten on disk. Browser assertions compare all graph keys and nested unknown metadata after actual visible edit/create/comment/switch/reload, alongside visible persisted task/comment assertions.
- New bookkeeping lives at `state.reactPanels[workspaceId]`: entity versions, command fingerprints/results, domain events and last observed storage revision. Workspace creation deduplication lives at `state.creationRequests`. Both are outside the record envelope and graph. The current local writer also preserves unknown record-envelope fields when saving.
- Each command runs inside the same `navigator.locks` key as the old writer, with a synchronous read/change/write callback. Without locks, the callback still does not yield between read and write. A successful batch persists once and advances the whole-workspace revision once; child commands see preceding child version changes. Failed validation/CAS/storage write leaves all stored graph/history/request bytes unchanged.
- React entity edits compare `expectedVersion`. Concurrent edits of the same entity yield one success and one version_conflict; unrelated entity writes preserve each other. A legacy writer can replace a record with the exact original `{id,data,revision+1}` shape. The top-level map survives. On revision drift, all known entity versions conservatively advance by that drift, forcing a stale React draft to reload rather than overwrite the legacy write. This conservative conflict is intentional when a whole-workspace writer cannot identify changed entities.
- Idempotency is persisted per device identity, workspace and key; signature includes operation, input and expectedVersion. Exact retries return the original result without another revision, comment, recurrence or event. Changed payload with the same key returns idempotency_conflict. Critically, a no-CAS add-comment replay after a literal old-writer record replacement returns the original result and leaves one comment. A dedicated regression checks this plus version monotonicity. Metadata is retained without automatic eviction in this gate.
- Completion/recurrence produces the next task, new subtask IDs/reset checkboxes, next key and due date in the same transaction. Recurrence uses existing 1/7/14/30-day behavior. Dependency cycles are rejected. Deleting a task/project requires explicitly unlinking dependencies or files referenced by surviving tasks before deletion.
- Local preferences keep `gr8r.preferences.<identity>` including unknown keys, prefs, collapsed, activeWorkspace and views[workspaceId]. Legacy local preferences/views import once, only to the original local workspace. Unknown legacy favorites/read state do not become a new identity's personal preferences. Appearance uses identity-specific settings, and `gr8r.auth.preferences` supplies the pre-auth language fallback; existing identity-specific language takes precedence, matching the original personal settings rule. System theme changes are observed by a scoped React listener.
- Local reads/results are cloned. Disposed requests retain their captured controller even after reactivation; queued disposed commands cannot commit. Storage quota/unavailable API throws and corrupt JSON/envelopes fail without seeding over existing bytes. Browser corruption and retained-draft conflict recovery are visibly covered. Origin-wide denial of every browser storage API is not separately claimed.
