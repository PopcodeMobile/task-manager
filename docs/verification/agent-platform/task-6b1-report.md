## Implementation and interfaces

`TaskList` retains its public status/priority label helpers and delegates to the exported `TaskViews` component. `TaskViewsProps` adds `repo`, `execute`, `table`, optional `projectId`, `viewKey`, `initialView` and `onViewChange`.6b4 can pass already-project-scoped tasks, its own URL/open callbacks and a saved-view key/configuration; there is no dependency on a project route implementation or legacy renderer. Rendering/editing helpers are in `TaskCells`, `TaskViewToolbar` and `TaskCoreActions`; filtering, grouping, ordering, command construction and personal-view persistence are in the pure `task-view-model.ts`. WorkspacePanel changes only inject these seams and move task query ownership into the view.

Implemented behavior:

- List/Board/Table links retain the current project/query route and open tasks through the existing guarded drawer. A single row DOM is adapted to mobile; no hidden duplicate task-title DOM. Secondary action names use the task key, preserving historical title-based task-opening locators.
- Search matches literal title/key. Filters support multiple selected values, AND between chips, is/is-not, editing/removing chips and clear. Fields: status, priority, member, project, due buckets, existing legacy label metadata, created/updated windows. Sorting: manual, title, due/start, priority/status, member/project, created/updated, estimate; direction reverses. Grouping: status, priority, member, project, due, none. Historical member IDs remain visible without invented people.
- Table columns can be shown/hidden/reset, and widths adjusted with accessible sliders, including the required title column. Actual column geometry uses colgroup widths; the browser test measures800px rather than merely checking stored state. Headers sort supported fields; graph columns expose the shared editor rather than pretending to edit relations. Inline title rename supports Enter/blur and Escape; status, member, priority, project, due/start and estimate use reviewed commands.
- Per-identity/workspace/view query, filters, sort, grouping, hidden columns, widths, collapse and show-completed choices use the existing `gr8r.preferences.<identity>` envelope. Writes merge current storage and retain unknown envelope/view keys. Existing legacy workspace view configuration is read as fallback; local bootstrap still performs its reviewed one-time migration. List/board/table/project/saved-view keys remain isolated.
- Group collapse/counts, contextual inline creation, native board/list drag, keyboard up/down ordering, status moves, board column complete/archive-completed/sort-priority and selection are implemented. Human assignment and executor identity remain distinct; executor names are displayed as literal metadata in rows/cards.
- Bulk status/member/priority/project/archive/delete uses one atomic batch. All selected IDs remain represented; selections above100 expose a visible bound and disable actions. Builders also bound actual child count. Active reservations preflight the whole selection and require explicit human intervention; there is no takeover command in bulk. Surviving task dependencies/files are not silently unlinked; deletion confirmation explains the requirement and the backend/local relation guard rejects the complete batch.
- Manual ordering uses a midpoint, and equal/precision-exhausted orders are renumbered atomically with CAS. Any rebalance requiring more than100 children is rejected before sending commands. Moving to Done composes the sort edit followed by `complete_task` at version+1, so actual cloud recurrence is not bypassed by `update_task(status=done)`.
- Drag data contains a random nonce created with the repository instance, not only a text task ID/workspace ID. Drop validates that nonce and membership in current tasks. A native browser test delivers an old-scope payload after switching to a workspace containing the same task ID and proves no mutation.
- Drawer start date/recurrence/estimate participate in save, fingerprint, clean hydration and explicit conflict recovery. Complete/move/duplicate/archive/restore/reopen/intervention/delete require an explicit successful save when the draft is dirty. The alert retains the draft and focuses Save. No stale completion followed by a late draft flush is permitted. Existing execution confirmation remains explicit.
- Successful duplication clears the completed draft guard before navigating to the returned clone ID, matching the existing successful-create/archive pattern. The tests assert a different URL/task ID and Todo state, not merely matching copied text. Archive and restore are verified through the same drawer, including reload/deep-link restoration for the future Archive route.

No adapter/DTO/handler/schema/storage-envelope changes were needed: the existing task command family already supports all consumed core fields. The actual checked LocalPanelTransport boundary, top-level reactPanels receipts, old-writer handling, local text IDs/unknown graph metadata, RPC envelopes, event boundary/read cursors, sessionBoundary, DraftGuard, abort guards and retry-key map remain unchanged.
