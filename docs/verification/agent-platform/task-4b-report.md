### Chosen contract and compatibility

Only `duplicate_file`'s `id` and `newId` change. They accept any PostgreSQL-representable Unicode string whose JavaScript `trim()` is nonempty and whose length is at most128 UTF-16 code units. No leading-character or punctuation restrictions. Input is kept exactly, with no trim rewrite, case folding, Unicode normalization or replacement. Thus `copy.v2`, `/copy`, `_copy`, `-copy`, `.`, `copy/v2`, `copy v2`, leading/trailing whitespace around a nonblank value, BMP Unicode and64 astral characters are accepted.128 ASCII characters pass;129 fail.64 astral characters (128 units) pass;65 fail.127 ASCII plus one astral character (129 units) fails.

This preserves every persisted source ID accepted by the existing shared cloud API. PostgreSQL-only IDs that were never accepted by that public shared validator, such as whitespace-only tab/BOM or strings exceeding128 UTF-16 units despite fewer PostgreSQL characters, are explicitly excluded for this new operation. NUL and lone UTF-16 surrogates cannot be stored by PostgreSQL and are rejected at the shared/local boundary; direct SQL JSONB decoding rejects them before the RPC body. The SQL tests assert this encoding rejection separately from the ordinary validation_error contract. They are not normalized into a different identifier.

Local validation bypasses the existing ASCII identifier regex exclusively for these two fields in duplicate_file. Other local operations keep their existing identifier rules. Shared validation adds explicit PostgreSQL representability checks for those same fields only.006 runs the existing strict validators first, bounding each ID to128 PostgreSQL characters, then uses the explicit ECMAScript whitespace set and counts each astral code point as two units. The supplementary counting loop therefore visits at most128 characters. OpenAPI field descriptions state the UTF-16 and whitespace semantics and the direct-SQL-only exclusions; its maxLength128 remains an outer code-point bound, with the stricter UTF-16 rule explicitly described. No other operation or migration001–005 changed.

Consulted primary references for the differing string semantics: [PostgreSQL string functions](https://www.postgresql.org/docs/18/functions-string.html) specifies that ascii returns Unicode code points under UTF8; [ECMAScript TrimString](https://tc39.es/ecma262/2024/multipage/text-processing.html#sec-trimstring) defines trimming using WhiteSpace plus LineTerminator. The ECMAScript definition controls the shared/local contract; SQL explicitly adapts its native character-count/default-btrim semantics. Mirrored fixtures also verify that U+0085, U+180E and U+200B remain accepted rather than accidentally treating every Unicode whitespace-like character as JS trim whitespace.
